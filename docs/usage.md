## Composer and voice input

Spec **#3685**, discussion **#3683**: below the draft, the first row has Add images, voice and Skill search on desktop and mobile; Stop Orc and Send stay at the right. The second row contains Discuss, Implement, Review, Re-review, Research and Diagnose (order spec **#3727**). On mobile only that second row scrolls horizontally. Skills prepare the invocation at the saved caret; sending still requires an explicit action.

On desktop and mobile, starting a valid ordinary message with Enter or Send releases the Composer input focus, leaving the conversation open. Click the input or press **I** to focus it again. This focus change does not confirm message acceptance; failed and unknown submissions retain their existing recovery behavior.

Voice settings are shared by signed-in users of the same instance. Choose Beijing or Singapore and save the region's DashScope API Key in Settings; switching regions requires a new key because keys cannot be used across regions. The default region is Beijing. The selected region is stored in workspace SQLite and the single key in `voice-api-key` next to the actual config file (`~/.config/flickgrove/config.toml`, or `--config PATH`). An existing private Beijing key at that location continues to work. The key is never returned by the settings API or stored in SQLite or TOML. Files with group/other permissions, empty/invalid keys, files larger than 1 KiB and missing/unreadable files make voice unavailable.

Each new connection snapshots the current region and key; a take already recording keeps its original snapshot. No restart is needed. When voice is unavailable, an open, visible conversation rechecks availability every 15 seconds so another user’s new key takes effect without a page refresh. Saving a key and saving the region are separate operations: if the key is saved but the database write fails, the API reports `key_saved_region_failed`. Select the correct region and retry with its key; until then the stored key and region may not match. Key file write failures leave the previous file intact.

Use HTTPS or localhost and a browser supporting microphone access, AudioContext at actual 16 kHz and AudioWorklet. Availability checks run silently; unsupported capture or missing/unavailable configuration disables only the microphone, with its reason in the title/accessibility description, and leaves text and images usable. Starting microphone, Recording elapsed time and Recognizing appear inline in the first-row Skill search slot; Skill search returns after success, cancellation or failure without adding a status row. Click the microphone to start; click Stop recording at the same position to recognize. From microphone permission/startup through recognition, the draft is read-only, Send/Skill/image changes are disabled, and Add images becomes Cancel. Stop Orc remains a separate execution action. Only the final text replaces the original selection or inserts at the captured caret; it never sends automatically or shows intermediate results. Failures/empty results preserve the draft. Cancel/Escape, hidden page, navigation, conversation/Peer changes, recovery and disconnection invalidate the take and release capture/transport resources; Escape preserves the existing foreground surface hierarchy.

Local voice capture and the fresh local instance capability/recognition connection prepare concurrently after an explicit microphone click. Recording and elapsed time begin on the first actual PCM frame, independently of server readiness. Up to five seconds (160,000 bytes) of startup PCM stays in memory; overflow fails the take instead of dropping speech. Only verified local instance ready permits ordered audio delivery. A short Stop flushes and releases capture immediately, then waits for readiness to deliver all retained frames before Finish. The 15-second startup bound remains effective while server readiness is pending, including during local Recording and after a short Stop; cancellation discards queued audio and invalidates late setup/results. No microphone or provider task is prepared before the click. Physical-device startup latency remains unmeasured.

The browser uses the current instance’s same-origin `GET /api/voice/capability` and WebSocket `/api/voice/stream`. Origin/address and stable instance identity checks guard access; no browser Peer credential is needed or accepted as cross-origin authorization. Agent MCP tokens remain separate. The key and raw provider frames never reach public state or the browser.

The relay selects fixed DashScope endpoints `wss://dashscope.aliyuncs.com/api-ws/v1/inference` (Beijing) or `wss://dashscope-intl.aliyuncs.com/api-ws/v1/inference` (Singapore), with `qwen-audio-3.1-asr-flash-streaming`, following [the official client protocol](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events). Capture streams mono PCM16 little-endian at 16 kHz in approximately 100 ms frames without buffering a whole recording or adding a resampling fallback. Limits: five minutes/9,600,000 PCM bytes, nonempty even frames up to 16 KiB, 256 KiB send queue, 128 KiB upstream events and 20,000 Unicode codepoints of final text; startup 15 s, finish 20 s, absolute relay lifetime 320 s from ready. Valid empty sentence finals close their interim segment without stopping recording; only usable text contributes to the final draft. Sentence finals are deduplicated and sorted by ID; invalid/unfinished/abnormal termination produces no draft change.

The relay does not persist or log audio or transcripts. The resulting draft uses the existing browser-local draft storage, and only an explicit Send creates a normal message. Cancel closes connections but cannot retract audio already streamed to DashScope or guarantee cancellation of provider processing/billing. No audio messages or service deployment are added.

Isolation verification: `bun test server/voice.test.ts` and `GROVE_TEST_AUTH_STUB=1 bun run test:browser tests/composer-voice.spec.ts` exercise synthetic private keys, fake upstreams and an actual AudioWorklet with synthetic microphone audio. Desktop 1440/mobile 390 screenshots are saved under `.scratch/composer-voice-two-rows/screenshots/`. Physical-phone microphone capture and real provider latency/billing are not verified by these tests.

## Managed workflows, Reviewers and Researchers

Spec **#5554** replaces the fixed #4776 assignment with a configurable default task division, captured by a new Orc from the instance's `prompts/role-division.md` and inherited by the Workers it creates. By default Orc handles work that directly shapes user or developer experience (interface layout, interaction and copy; developer-facing commands and wizards; Blender models, scenes and visual animation), important long-lived data contracts (database schema and migrations), one-off ops scripts and agent instructions; a sole Worker owns other implementation, including reusable Blender and engineering tools. The user's explicit assignment for the current task overrides that default, but Orcs and Workers created earlier keep their captured rules: restart, restoration and new owned Workers never adopt a changed file. Each owner handles its tests and fixes. Orc investigates and decides before dispatch, framing irreducible technical unknowns as bounded evidence tasks. Mixed work shares one PR and checkout, with serial edits preserving each owner's changes. Orc creates the PR and updates its title and description when needed. Orc chooses minor unspecified visual details using existing styles; potential client-impacting interface changes and undecided material workflow or interaction alternatives go to the user with their effects. This managed guidance supersedes conflicting confirmation guidance in older captured task divisions. Orc substantively self-reviews the whole diff, spec, evidence and complexity. Independent whole-PR Standards and Spec review (high-risk Spec where appropriate) follows the organization setting captured when the Orc was created and the user’s task-specific direction. Reviewers read code and existing evidence without running verification; missing evidence goes to the relevant owner. One-off ops without a PR receives Orc self-review and independent review on user request; execution still requires authorization. Existing tickets are read; new tickets are created only on explicit request.

Each local instance initializes `~/.config/flickgrove/config.toml` and adjacent `prompts/` from versioned repository templates before serving. `--config PATH` selects an explicit configuration path. Initialization creates only missing files, retries partial initialization and adds newly shipped prompt files; existing customization is never overwritten. Invalid/missing Orc prompt or Reviewer profiles and unreadable/empty explicit prompts fail clearly. Relative prompt paths resolve against the configuration directory. Role prompts are configured here; every Worker, Reviewer and Researcher model comes from the instance's current member preset. Profile changes affect subsequent newly created members; existing members and re-review retain their captured prompt text and model in workspace state. There is no prompt hot reload.

```toml
[reviewers.standards]
prompt_file = "prompts/standards.md"
```

## Connections and browser preferences

Use `--listen`, `--port` and `--origin` for an existing HTTP(S) proxy/tunnel. This application does not provision tunnels. The configured origin has no path, query or embedded credentials. Proxies preserve Host, Origin, X-Grove-Peer and WebSocket upgrades/subprotocols on `/api/socket` and `/api/voice/stream`. Local agent MCP calls use `http://127.0.0.1:PORT` and separate per-agent tokens, independently of the advertised browser origin.

`--state DIRECTORY` selects durable state (default `~/.local/share/flickgrove`); `--codex PATH` selects the executable. `workspace.sqlite` owns conversations and captured tree execution settings. `hosts.json` retains the stable local instance ID used to namespace browser caches and pending submissions. New files contain only the ID. Existing files are read without rewriting; obsolete credential fields have no authority. No saved sessions or pending operations are migrated or deleted.

Same-origin browser sockets use the page Origin and `grove.v1`; no Peer token is needed. Legacy bearer headers or auth subprotocols do not affect same-origin access. Foreign and missing browser origins are rejected, even with a former Peer token. Reading/media requests allow same-origin Fetch Metadata when Origin is omitted. Chord carries local calls and replicated list/selected-detail state. Instance-qualified IDs preserve durable ownership and pending receipt identity; they never select a remote route. Agent MCP tokens never appear in public state.

Settings save this browser’s **new-session preferences**: the Orc model and effort, and Fast. Worker, Reviewer and Researcher models come from the instance’s current **member preset**, shared by the whole instance and editable as TOML files (see [Member model presets](operations.md#member-model-presets)). Creation selects a local registered project and explicitly sends the Orc settings to this instance, which validates capabilities without silently downgrading. Each tree captures its Orc execution settings, including across restart, and each member captures its preset choice at creation. Later browser preference or preset changes do not modify existing members.

Press **N** to search registered projects immediately by alias or name. Arrow keys browse and Enter chooses a project; **New session** creates it. Find history preserves that project search when returning. Model choices are searchable and show their provider and ID; backend and effort use the same project-styled choice controls. Escape or browser Back dismisses an expanded choice before its containing dialog. Unavailable saved choices stay visible until explicitly replaced.

The opened Orc has an individual **Session settings** control for Model and Reasoning effort with atomic Save/Cancel (**Option/Alt+M**); a Worker, Reviewer or Researcher shows its captured model and effort read-only. A separate **Tree Fast** Zap control (**Option/Alt+F**) targets the owning Orc and all open editable Workers, Reviewers and Researchers, and sets the Fast policy for future Workers. The Orc list indicator shows this desired tree policy. Unsupported models stay on their original model at standard speed; the control tooltip explains capability and the confirmed next-turn tier. Orc model/effort changes affect only that Orc and recompute its tier from the tree policy. Physical-key shortcuts preserve Composer drafts/selection; IME, title editing and foreground panels block them.

Changes use native `thread/settings/update` on original shared app-server threads. Each member's confirmed settings remain authoritative; multi-thread updates are not atomic. Explicit tree mutations persist desired policy within the owning tree; other trees, model/effort defaults and browser new-session preferences remain independent. Changes affect subsequent new turns; current work and `turn/steer` retain their configuration. Partial failure or unknown outcomes remain actionable beside the control. Explicit Retry first reads native settings before any necessary update; no automatic replay, rollback, new process, message or turn occurs. One in-flight tree action excludes concurrent starts, model saves and closure. Existing tree policy derives from the owner's current setting until explicitly changed.

First opening a known agent immediately displays its target identity and stable Composer, while only the transcript loads. Draft typing is available; Send, Stop, title and settings mutations wait for authoritative detail. Arrival preserves Composer focus, caret and draft. Failure retains the frame with localized Retry. Cached history and reading positions retain their existing bounded browser-memory contract.

The native recent window and device-local pending messages are readable immediately. On a first visit, server recovery records wait for the first HTTP history check, with a localized loading status beside the recent content. Successful native identity matches retire temporary recovery rows; a failed read keeps unresolved records accessible and permits Retry without inferring that the Peer is offline or replaying submissions. Cached native reading remains immediate.

A new Codex session saves its existing Grove title with native `thread/name/set` before creation succeeds. This persists an unsent paginated thread for passive reading after restart. Rejected, disconnected or timed-out saves fail creation without automatically repeating creation or naming; an unknown save may have persisted native state. Restoring an existing thread preserves its native title. Passive history never names, resumes or sends to repair missing history.

A freshly started native thread is known empty until a send is attempted or a native event arrives. During that interval Grove serves an empty reading page without invoking native item listing, so a new unsent session shows its first-input state. This knowledge ends on release or connection replacement; resumed threads and uncertain sends still use normal native reads and expose genuine errors with Retry.

## Conversation controls and usage

Press **N**, choose a local registered project, then select **Find history** to search that directory's Codex and Pi sessions by title or first message. Codex results include CLI and archived sessions; Pi results are Grove-owned Durable sessions, including closed members. Search uses native history and app-server `thread/list` and directory identity, including canonical aliases; Grove does not build a second search index or transcript.

Conversation bodies come from native items. Complete non-empty assistant messages, including commentary, appear as soon as their native item completes, while the turn may still be working. Generated text deltas are never displayed as message content; there is no word-by-word output. History reads use the same completed-item boundary and native IDs, retaining completed messages after failure or Stop without duplicate rows. Completion identities are retained only for the active turn, including native history messages admitted by detail synchronization, so replaying an evicted item cannot move it to the reading end. This transient set stores IDs, not message bodies, and is released when the turn ends or is replaced, or the agent closes. Completed messages publish immediately without a history query, even when history reads fail. Ordinary messages remain conversation content; collaboration reports still require the explicit report tools. Selection and reconnection establish a recent window from the current native state, merged with arrivals during the read by item ID. The server continuously slides that window within 100 messages and a 256 KiB encoded message budget. Chord retains its existing 2 MiB frame limit; it carries bounded detail, submission receipts and work state. Earlier messages and read-only previews use direct HTTP fetch to the local instance. A page contains at most 100 messages within a 1 MiB encoded response budget, including source metadata. If the native page exceeds the budget, an opaque reading cursor records the oldest returned item and native position so the next read does not skip omitted items. One oversized item carries its identity and a full-body reference, with **Read full message** and independent Retry; expanding a report reads that same native body.

Spec **#130** presents classified assistant progress normally until a result appears, then groups the loaded preceding progress in **Work details** before that result. Identified Worker, Reviewer, and Researcher messages are hidden from the browser Orc transcript in every delivery state; the original messages and their delivery to Orc remain unchanged. User inputs, Orc-authored questions, their failed or uncertain deliveries, and unclassified messages stay visible. Older pages can extend a group; absent classification never hides a message. The view leaves native messages intact. Incoming content and layout changes do not automatically follow the bottom; use the jump button or **Cmd+Down** / **Ctrl+Down** to return to the latest content. **Cmd+Up** / **Ctrl+Up** jumps to the top of the loaded transcript. A first visit starts at the latest content and revisits retain the reading position.

Codex ordinary input, steer and collaboration reports send their existing operation ID as `clientUserMessageId`. Native `userMessage.clientId` associates each item with its delivery source and original Worker/Reviewer/Researcher identity, including after closure. Native item ID deduplicates content; turn ID and equal text do not establish report identity. Identified member reports and their delivery states stay out of browser Orc presentation in every state, including forwarded member questions. Orc-authored questions remain visible. Old messages without clientId remain ordinary readable native messages, without identity backfill. Admission and notification may arrive in either order; the matching provisional operation converges to the native item.

Loaded native pages, slid reading items and their next cursor use the existing browser-memory LRU, keyed by Peer-qualified conversation and native thread (12 conversations and 8 MiB of serialized UTF-16 reading material). Revisits restore content and reading position together. Closure/removal invalidates its entry. Cancellation and request generations isolate old loads from a switched conversation. A failed earlier page retains content and cursor for explicit Retry and does not take the realtime connection offline or affect submission. Offline visits retain available reading material. Native historical pages and DOM are not persisted as a second transcript.

The durable delivery ledger retains complete recovery text, images, question identities and answers before sending. Realtime detail projects bounded metadata, with original-identity HTTP reads for full recovery and Questions material. Older unresolved submissions remain available through **Earlier submissions**. Lookup remains accepted/rejected/null independently of the current window or browser cache. Null never authorizes a resend or implies rejection; clientId is correlation, not a native idempotency or consumption guarantee.

Codex execution backends must support `clientUserMessageId` on start/steer, `userMessage.clientId` in both notifications and durable `thread/items/list`, and opaque item pagination. Isolated installed Codex 0.160.0 verification covers start/steer, item events, pagination and original-thread resume with a local fake provider and private test-owned homes; older preparation-machine version claims are not runtime evidence. Deploy the frontend assets and local backend together: the old history-body Chord RPCs are removed. Proxies must preserve `/api/read/*` HTTP requests, Authorization, X-Grove-Peer, Origin, OPTIONS preflight and response identity/CORS headers, like `/api/images`. Reads contact the local instance directly and never forward through the local instance. Deployment and live state migration/cleanup are separate from this change.

Conversation messages show compact local times, with short dates on previous days and full date/time plus timezone on hover. Native history uses recorded item lifecycle millisecond timestamps when available; missing times are omitted. User messages prefer item start time and assistant messages prefer completion time. Live messages retain their observed lifecycle or submission times; pending submissions use their browser submission time until confirmed by the local instance.

Resume continues the original thread without sending a message. CLI sessions become Orcs with their existing model, reasoning effort and service tier; closed Grove Orcs retain their identity and keep old Workers closed. Workers remain read-only and link to their owning Orc. Already open sessions open their existing detail. Codex's writer lock rejects sessions held by another instance; the preview shows the error and permits explicit retry after that instance releases it. Grove never removes locks or forces ownership. The execution host must run a Codex app-server supporting indexed `thread/list`, paginated items and writer locks.

Open-session rows and history results use two compact lines. Execution state and input needs sit at the upper-right, while Worker disclosure and counts share the metadata line. They do not consume separate rows. The open-session metadata line includes a muted Lucide GitBranch indicator, with branch text capped at 12ch, ellipsis and the complete value in its title. It shows the current checkout of the session’s registered working directory, including a worktree’s own branch; it does not track tool-local `cd` or freeze the branch at creation. Workers sharing their Orc’s directory omit the duplicate indicator; a different directory shows its own value even when branch names match.

Each local instance deduplicates open-session directories (including symlink aliases), reads local Git metadata promptly on startup/new directories and polls about every five seconds after a completed cycle. At most two reads run concurrently, each Git subprocess has a 1.5-second limit, and no network Git operation runs. Only changed values publish through the existing Chord snapshot/detail and Peer-specific browser cache. Non-repositories show nothing and explicitly clear an earlier value; detached HEAD shows `@` plus a short commit, and unborn branches show their name. Query failures and offline Peers retain the last successful value, with no unknown placeholder or freshness label. Closing the last session stops its directory’s reads; shutdown aborts queries and discards late results. Branch state stays in Peer memory, without a database copy, and is reread on Peer startup.

Send ordinary instructions to Orc. An idle Orc uses native `turnStart`; new input during execution uses `turnSteer` immediately in submission order, without waiting for the model’s answer. Each submission has its own stable operation ID, separate from a socket request ID and native turn ID. The browser persists each operation in its own origin/agent-scoped record before invocation, so another tab cannot erase pending content or identity. It echoes it immediately and clears the submitted draft so editing and further sends remain available. Sending stays disabled while offline or Stopping, while an offline draft remains editable.

While an Orc is working, Tab in the composer or the queue button places a follow-up after the current turn. The list above the composer shows waiting messages and permits their removal. Grove stores and schedules this queue for both Codex and Pi; it is not the Codex native thread queue. Grove advances one message at a time after a verified completion and keeps attachments with their operation. Stop and confirmed Close retain and pause the queue; after reopening, Continue requires a verified safe boundary. An unverified outcome also pauses it. Check looks up the original operation and separately reports receipt and turn completion; missing evidence remains unconfirmed and never triggers a resend. A session with pending follow-ups remains active in Recent; confirmed Close retains its queue in a paused state. The original draft and operation identity remain on the device until queue admission is confirmed; a disconnected or timed-out admission can be checked without resending. Offline queue displays are retained reading copies, not current confirmation. Grove has no product workflow for Codex Goals; externally managed native queues or Goals are outside this queue's behavior.

An accepted receipt proves native input acceptance, not model consumption or completed work. Rejected messages retain their reason and recovery action. An explicit retry of a rejected message or answer reserves one direct successor; only the request that wins that reservation receives the one-time sending capability. A lost winner response permits checking or finalizing a still-reserved successor, not sending it. The original and successor remain in the durable ledger; a read-only retry relationship does not prove native acceptance. Native history is checked before a retry, although eventually consistent history can still omit a late acceptance. Unknown operations are inspected by their original ID and are never automatically resent. Ordinary messages and submitted answers remain visible as normal conversation entries while Grove reconciles the original operation. An unconfirmed or rejected answer batch cannot be answered again; other unanswered batches remain available. A definitive rejection offers its reason and explicit retry beside the original content. A question that another answer already confirmed refuses a duplicate. Failed Worker reports retain explicit Retry with their original report identity; unresolved reports retain their existing delivery feedback and closure guard.

A manual title takes precedence. This application does not create, merge or deploy PRs itself.

Backend startup reads Orc names without resuming turns; explicit thread resume refreshes them again. Unreachable Codex reads retain the last cached title. Changing a title sends no model message. `worker_close` records a durable closure request. A ready Worker closes after native thread release succeeds; a running Worker completes its current turn without interruption and closes automatically once its reports are delivered and delegated questions are answered. Pending Workers show Closing and a waiting reason and reject new tasks; explicit answers to existing questions remain allowed. Failed terminal turns also permit closure. Restart or disconnection retains the request with an unknown outcome; Orc can inspect it and explicitly use `confirmInterrupted` to acknowledge the interruption, while report and question guards still apply. A verified failed turn also lets the Orc itself close: Pi reports a failed provider turn as a settled terminal error, and that state no longer counts as still working. Agent workflows still leave child lifecycle with Orc. User-initiated Close tree instead preflights all open owned roles and releases eligible children before Orc, without a model instruction or Stop. Orcs and Workers stay visible with their handles until native unsubscribe succeeds. A failed release keeps them retryable: retry direct Close for Orc, or `worker_close` for Worker; automatic Worker release failure shows its reason and waits for an explicit retry. History restore refuses while ordinary tree Close is in flight and reuses an agent whose failed release kept it open.

Every UI **Close** opens a confirmation. A known working or stopping Orc or member cannot close; no prompt or Stop is sent. Confirmation accepts pending questions, reports and unknown delivery or execution outcomes, which remain recorded without being inferred as completed or resent. Unknown work may still be running. Pending messages and images held only on this device remain available when the session is reopened. Waiting follow-ups remain paused after reopening and require explicit Continue. The browser records the close intent before sending and checks the original session after an unknown response; it never replays the close automatically.

Confirmed closure fences new tree operations, checks current activity and revalidates during native release. A release or storage failure can leave a partially closed tree; the remaining sessions stay available for inspection. When a closed Pi Orc is explicitly reopened, Pi Durable may resume its previously accepted native work; its Grove waiting follow-ups remain paused until Continue. Previewing native history remains read-only. The older explicit abandonment call remains supported for existing clients.

Incoming member reports and their delivery statuses stay out of browser Orc presentation in every state. The native transcript and delivery ledger retain failures, uncertain outcomes and original identities without automatic replay. Source and sender identity are taken from existing delivery metadata; no report storage is added.

Chat Markdown, historical conversations and expanded Worker reports render math with the existing SvelteMarkdown `markedKatex` extension and KaTeX. Math cannot enable trusted HTML or links. Fonts and CSS are bundled locally, and long formulas scroll within the message. Generated-file Markdown previews retain their separate rendering behavior.

Fenced `mermaid` diagrams load on demand in the shared chat renderer, use strict read-only rendering and the dark theme, and show their source if rendering fails. Long diagrams scroll inside the message. Ordinary fenced code uses TanStack Highlight through the SvelteMarkdown adapter, with one shared highlighter for JavaScript/TypeScript/JSX/TSX, JSON, HTML, CSS, Python, shell, SQL, YAML and Svelte. Unknown or missing languages remain escaped plaintext; long code scrolls locally. These additions also apply to history and expanded Worker reports.

## Message images

Use **Add images**, paste image files or drag files into Composer. A message can contain text, images, or both. Remove any preview before sending. Limits: PNG/JPEG/WebP/non-animated GIF, up to **5 images**, **5 MiB each**, **20 MiB total**, **40 megapixels**, and **16383 pixels per side**. The local instance validates actual format and complete decoding; changing a filename or declared type does not bypass validation. Errors stay beside the draft or submission.

Full dimensions and decoded screenshot detail are retained. Sharp/libvips encodes true lossless WebP; it is adopted only when smaller and decoded RGBA matches exactly, including alpha. Otherwise the original bytes remain. Separate WebP thumbnails fit within 480px and 160KB; full images load on demand. File size does not establish model token cost or native consumption.

Image blobs persist in origin-scoped IndexedDB under the local instance/Orc, with a 200 MiB/200-record device bound. Storage failures preserve the draft. After reservation, submission journals the text and attachment snapshot before uploading; slow uploads, switching sessions or newer drafts cannot move it. An interrupted upload may reuse local attachments under the same operation ID to restore image references without sending native input. If local files are unavailable and the server has no references, the outcome remains unknown. Explicit retries bind the same content and verify image fingerprints; a different device can use a retained server original when it can be verified. Unknown outcomes never automatically resend; accepted receipts outrank late errors.

The browser uploads and reads from the current instance with origin/address and instance identity checks. Cross-origin uploads and reads are refused; no bearer token enables them. Chord retains its 2 MiB frame limit and carries stable references only. Upload completion is separate from native admission. Native localImage inputs contain only validated stored paths; browser input cannot request arbitrary files. Proxies must permit `/api/images` bodies up to about 21 MiB and preserve Origin/X-Grove-Peer for GET/POST.

Sharp is a runtime dependency installed by `bun install`; its supported platform binaries include libvips. The selected `--state` directory now contains private `media/` files and an atomic index, alongside workspace state. Unsubmitted uploads expire after 24 hours, checked on startup/upload, and are bounded to 100 operations/200 MiB. Referenced submissions and imported historical attachments are retained. Keep media with the workspace when backing up state. No deployment or restart is part of this change.

Spec **#3607** fixes multipart caption newline conversion: the upload's `text` field is a JSON-encoded string, decoded once before storage, so it exactly matches the original Chord submission. Agent, Peer, operation, text and ordered image-reference checks remain exact; no normalization, compatibility fallback, stored-media migration or automatic replay is added. The bounded HTTP body allowance includes worst-case JSON escaping of a 100,000-unit caption; image limits remain unchanged. Isolated browser/HTTP/Chord tests cover multiline acceptance, tampering rejection, deduplication and draft recovery. Update browser and backend together during the separately authorized deployment.

Sent Grove images and recoverable native thread image/localImage attachments display through authorized opaque references. Native membership is verified from that thread's actual item history; arbitrary paths and external image URLs are never fetched on browser request. Missing, unreadable, unsupported or oversized native attachments show an explicit placeholder; recovery of every historical attachment is not promised.

Execution feedback uses the fixed detail heading’s existing state/time position for Orcs and read-only Workers. Working shows the current turn’s elapsed time; Retrying appears only with explicit native `willRetry` evidence and keeps that time. Model at capacity and Execution error describe terminal failures with no active timer. Expand the status to read the full reason in a bounded scrolling area; the transcript does not repeat it. Current-turn native progress (non-empty agent delta, non-user item start or agent item completion), successful completion and a new native turn clear old feedback; steer admission alone does not. Thread/turn identity isolates late events. Codex owns request retries and stream recovery; Grove adds no retry, model switch or Worker creation. Disconnections and individual failed/unknown message recovery retain their own feedback.

There are no slash actions or proactive compact controls. A Working Orc has a circular stop-square button beside the independent circular Send button. Stop has no visible text; its tooltip and accessible name remain **Stop Orc**. Stop calls official SDK interruption for the **observed current Orc turn ID**; it never stops Workers. Stopping stays pending until an authoritative completion arrives. Confirmed user interruption returns Idle and shows feedback; a normally completed turn shows its actual outcome. Unknown acceptance stays unknown, never becomes success on a timer and never stops a later turn through replay. Reports, questions and uncertain deliveries remain available and retain close guards. A report received while Stopping is retained for explicit retry after the turn outcome.

**Option+X** on Mac or **Alt+X** elsewhere closes the current Orc tree: an open Orc detail takes precedence, otherwise the unique navigation Orc is the target. A Worker never implicitly closes its parent. The shortcut also works in ordinary Composer input, blocks character insertion, and pauses during temporary surfaces, title editing or IME. On mobile, swipe an Orc row left to reveal **Close this tree**, then tap to execute. Only one row exposes the action; swipe right or tap outside to collapse it. Vertical scrolling and ordinary row taps remain available, and Workers have no tree-close action. Close uses a dedicated Chord `closeTree` call directly to its execution owner, without sending a user message. Every Close asks for confirmation; the dialog reports known running members, unconfirmed work, unanswered questions and queued messages. Known working or stopping Orcs and members cannot close. For confirmed closure, Grove retains questions, delivery facts and history, pauses waiting follow-ups, preflights and releases members before the Orc, and checks for changes during release. Unknown work is not assumed to have stopped. A failed or unconfirmed release is reported without automatic replay; closed members stay closed. Close results lost in transit are checked through the original Peer, rather than inferred from list absence. Refusal details appear in the affected session detail. **Zero Workers is only a current count**; the application does not infer task completion or suggest closing from it.

The upper-right weekly inner ring and adjacent percentage both show **quota used** from the local instance. The current instance supplies quota and model catalogues. The instance validates model, effort and Fast capabilities when creating or updating sessions. The quota reader chooses the official window with `windowDurationMins: 10080`, regardless of primary/secondary position. Remaining is clamped `100 - usedPercent`; missing data is a dash until a valid instance cache exists. Quota buckets are never summed. ## Generated file previews

Click a local PNG/JPEG/WebP/GIF, HTML/HTM or Markdown link in an Orc/Worker message, restored conversation or expanded Worker report to read it beside the conversation. HTML retains its own presentation and can run scripts and load external HTTP(S) CDN resources. Both the embedded frame and directly opened HTML/Markdown use a browser sandbox with scripts allowed and same-origin, forms, popups and top navigation permissions withheld. Markdown escapes raw HTML and keeps code/table scrolling local to the content. This supports standalone reports, not a development server or general web application. No download control or arbitrary HTTP/localhost proxy is provided.

Preview access uses a random, short-lived bearer capability scoped to the local instance and canonical resource directory, held only in memory: 15 minutes, at most 256 grants per instance HTTP handler. Each resource read verifies that the issuing session remains active; logout, session expiry or targeted recovery revokes its grants.
